# AI API Rank

一个以表格为核心的 AI API 中转站排行榜，用同一份公开数据对比站点的在线率、响应延迟、模型覆盖、用户评分、支付方式、退款和发票支持。

> 计划访问地址：[https://aiapirank.github.io/](https://aiapirank.github.io/)
>
> 排名只是筛选入口，不是对任何站点的背书。正式使用前请自行验证模型、账单、隐私政策和服务稳定性，并坚持小额充值。

## 先看结论

| 优先级 | 应该看什么 | 为什么重要 | 建议动作 |
| ---: | --- | --- | --- |
| 1 | 长期在线率 | 决定服务是否经常中断 | 至少观察多个时段，不用一次测速下结论 |
| 2 | 平均延迟与波动 | 决定聊天、编程和并发调用体验 | 在工作日、晚高峰分别测试首字延迟和完整响应时间 |
| 3 | 模型真实性 | 低价模型可能被映射、降级或限制能力 | 用固定测试集核对模型版本、上下文和工具调用能力 |
| 4 | 真实计费 | 标价之外还可能有充值、模型和缓存倍率 | 检查逐请求账单，核对输入、输出和缓存 Token |
| 5 | 运营与售后 | 故障通知、退款和发票会影响长期使用 | 确认运营主体、客服渠道、退款规则和状态公告 |
| 6 | 余额风险 | 中转站可能调价、停运或更换上游 | 用多少充多少，不囤大额余额和长期套餐 |

## 什么是 AI API 中转站？

中转站位于开发者与上游模型服务之间。开发者把请求发送到中转站，中转站完成鉴权、余额检查、模型映射和路由，再把请求转发到官方 API、云平台接口或其他上游渠道。

| 请求阶段 | 发生了什么 | 需要关注什么 |
| ---: | --- | --- |
| 1. 客户端 | 应用、脚本、Claude Code 或 Codex 发出请求 | Base URL、API Key、模型名称是否配置正确 |
| 2. 中转鉴权 | 平台验证 Key、额度和请求权限 | Key 是否可以限制额度、模型和 IP |
| 3. 模型路由 | 中转站把模型名映射到具体上游 | 是否明确模型版本，上游是否会自动切换 |
| 4. 上游调用 | 请求进入官方 API、云平台或号池 | 稳定性、速率限制、上下文与工具能力 |
| 5. 账单结算 | 平台按 Token 和倍率扣除余额 | 输入、输出、缓存、失败请求是否分开记录 |
| 6. 返回结果 | 响应经过中转站返回客户端 | 流式输出、错误码和官方接口是否兼容 |

中转站主要解决国内用户常遇到的国际支付、网络可达性、多厂商账号管理和统一接口问题，但也增加了第三方可见请求内容、上游不透明、模型映射、计费以及平台停运风险。

## 官方订阅、官方 API 和中转站怎么选？

| 维度 | 官方订阅 | 官方 API | 中转站 |
| --- | --- | --- | --- |
| 典型用途 | 官方网页、桌面端或官方编程工具 | 自建应用、自动化与生产 API | 低门槛接入多个模型或兼容工具 |
| 计费方式 | 固定月费或套餐额度 | 按 Token、图片或请求量计费 | 官方价格基础上叠加平台汇率和倍率 |
| 支付门槛 | 通常需要官方支持地区的支付方式 | 通常需要海外支付与合规网络环境 | 常见微信、支付宝、USDT 或对公转账 |
| 模型覆盖 | 单一厂商生态 | 一个官方账号对应一个厂商 | 一个 Key 可能接入 Claude、GPT、Gemini、Grok 等 |
| 稳定性 | 官方维护 | 官方维护 | 同时依赖中转站与上游 |
| 隐私性 | 请求直达官方产品 | 请求直达官方 API | 请求经过第三方系统，理论上可能被记录 |
| 账号风险 | 用户承担订阅账号风控 | 用户承担 API 账号与支付风控 | 部分上游风险由中转方承担，但服务可能突然中断 |
| 适合谁 | 重度使用官方客户端的人 | 对隐私、稳定性和合规要求高的团队 | 希望快速接入、统一管理多个模型的个人或小团队 |

简单判断：

| 你的情况 | 更适合的方式 |
| --- | --- |
| 有海外支付条件，对隐私和稳定性要求最高 | 官方 API |
| 主要在官方网页或官方客户端重度使用 | 官方订阅 |
| 需要国内支付、快速接入或一个 Key 使用多家模型 | 中转站 |
| 正式生产业务、含敏感数据 | 优先官方 API；如必须中转，应完成供应商审查和数据脱敏 |

## 中转站的价格是怎么算的？

不要只看“充值 1 元得到多少额度”。实际成本通常由多层参数共同决定。

| 价格参数 | 含义 | 常见误区 |
| --- | --- | --- |
| 官方模型价格 | 上游模型每百万输入、输出或缓存 Token 的价格 | 只看输入价，忽略更贵的输出 Token |
| 充值汇率 | 人民币充值后换算成多少美元或平台额度 | 把“1 元 = 1 美元额度”误认为按官方汇率结算 |
| 模型倍率 | 某个模型在平台上的额外计费系数 | 首页低倍率可能只适用于部分渠道或分组 |
| 分组倍率 | 普通、稳定、高并发等线路可能使用不同倍率 | Key 被分配到更贵分组后没有及时发现 |
| 缓存价格 | 缓存写入和命中读取的单独费率 | 长对话里忽略缓存，导致成本远高于预估 |

可以用下面的简化公式估算：

```text
实际扣费 ≈ 官方 Token 费用 × 模型倍率 × 分组倍率 ÷ 充值换算率
```

示例：某次官方费用为 `$5`，平台充值规则为 `¥1 = $1 平台额度`，模型倍率为 `1.5`，分组倍率为 `1.0`：

```text
$5 × 1.5 × 1.0 = 7.5 平台额度 ≈ ¥7.5
```

这只是演示。每个平台对额度、美元、倍率和缓存的定义可能不同，应以它自己的价目表和逐请求账单为准。

## 为什么缓存费用很关键？

Claude Code、Codex、长对话和大型代码库分析会反复发送大量上下文。缓存命中时，重复内容通常比普通输入便宜；一旦缓存失效，成本可能快速上升。

| 场景 | 成本影响 | 检查方法 |
| --- | --- | --- |
| 首次发送长上下文 | 通常按普通输入或缓存写入计费 | 查看账单是否单列 cache write |
| 后续请求命中缓存 | 理论上应显著低于普通输入 | 比较 cache read 与普通 input 单价 |
| 中转站切换上游账号 | 既有缓存可能全部失效 | 观察连续对话中缓存命中率是否突然归零 |
| 使用超长上下文 | 上下文越长，失效后的重算成本越高 | 没有明确需求时，不要盲目使用 1M 上下文 |
| 平台不展示缓存明细 | 无法判断实际倍率与命中情况 | 先小额调用并要求可核对的明细账单 |

超长上下文并不等于效果一定更好。上下文过长时，模型可能遗漏中间信息；如果中转号池发生切换，已经建立的缓存也可能失效。

## Claude Code、Codex 和 Grok 需要注意什么？

| 工具或模型 | 需要确认的内容 | 常见问题 |
| --- | --- | --- |
| Claude Code | Anthropic Messages API 兼容性、流式输出、缓存与工具调用 | 模型名称被映射、缓存不透明、长任务中途切线 |
| Codex | OpenAI API 兼容性、Responses API 支持、推理模型参数 | 只兼容旧接口、工具调用字段不完整、模型版本落后 |
| Grok / xAI | 模型版本、上下文长度、图像或工具能力 | 使用兼容名称但能力与官方版本不一致 |
| OpenAI 兼容接口 | Base URL、错误码、流式事件和 JSON 字段 | “兼容”只覆盖基础聊天，复杂接口无法使用 |

官方订阅账号、官方 API Key 和中转站 API Key 是不同的使用方式。购买前应先确认目标工具支持哪种认证和接口，不能只根据模型名称判断。

## 怎么判断一个站是否靠谱？

### 值得优先检查的指标

| 指标 | 更理想的表现 | 不能单独说明什么 |
| --- | --- | --- |
| 在线率 | 长期高于 99%，高峰期无明显下降 | 100% 但只有很短监测周期 |
| 延迟 | 多时段稳定，首字和完整响应时间波动小 | 某一次测速特别快 |
| 模型更新 | 官方新模型发布后及时跟进，并标明版本 | 后台列了很多无法实际调用的模型名 |
| 账单透明度 | 每次请求可查模型、Token、倍率、缓存和费用 | 只显示余额减少，没有明细 |
| 运营信息 | 主体、客服、公告、退款和发票规则清楚 | 首页宣传语或群内口头承诺 |
| 风险控制 | Key 可限额，可查看日志，可快速禁用 | 只提供一个无限额主 Key |

### 需要警惕的信号

| 风险信号 | 可能的问题 | 建议 |
| --- | --- | --- |
| 高价模型长期低得离谱 | 模型替换、特殊渠道、能力限制或不可持续补贴 | 用固定测试集验证，不直接迁移正式业务 |
| 只接受大额充值 | 现金流或停运风险更高 | 不充值，或只投入可以完全损失的金额 |
| 不展示逐请求账单 | 无法确认倍率、缓存和异常扣费 | 放弃用于正式业务 |
| 模型版本和上游含糊 | 可能自动降级或切换来源 | 要求明确说明，测试关键能力 |
| 故障时没有状态通知 | 运维和客服响应能力不足 | 查看历史公告和用户群中的真实处理记录 |
| 退款、发票规则临时变化 | 运营规范性不足 | 保留规则截图和交易凭证，控制余额 |

## 上线前的 5 分钟测试

| 步骤 | 测试内容 | 通过标准 |
| ---: | --- | --- |
| 1 | 充值最低可用金额 | 支付到账和余额换算符合页面说明 |
| 2 | 调用最常用模型 | 模型名、输出质量和关键能力符合预期 |
| 3 | 检查一次完整账单 | 输入、输出、缓存、倍率与最终扣费可以复算 |
| 4 | 连续发送 10～20 次请求 | 无明显错误峰值，延迟波动可以接受 |
| 5 | 测试流式输出和工具调用 | 与目标 SDK、Claude Code 或 Codex 兼容 |
| 6 | 设置 Key 限额 | 单个 Key 泄露时不会耗尽全部余额 |
| 7 | 查找客服和状态入口 | 出故障时知道在哪里看公告、提交工单 |

## 排行榜数据说明

页面读取根目录中的 [`data.json`](./data.json)。当前文件与 `awesome-ai-api` 项目中的数据快照保持一致，数据来源为 [禾维 AI](https://www.hvoy.ai)。

| 字段 | 页面含义 |
| --- | --- |
| `rank` | 当前综合排名 |
| `name` / `url` | 站点名称与详情链接 |
| `uptime` | 监测得到的平均在线率 |
| `latencyMs` | 平均响应延迟，单位毫秒 |
| `modelCount` | 收录的模型数量 |
| `models` | 覆盖的主要模型厂商 |
| `userRating` / `ratingCount` | 用户评分与评价数量 |
| `paymentMethods` | 已知支付方式 |
| `supportsRefund` | 是否明确支持退款；`null` 表示待确认 |
| `supportsInvoice` | 是否明确支持发票；`null` 表示待确认 |

在线率与延迟会因监测时间、地区、线路和上游状态变化。退款、发票、价格和模型信息也可能随时调整，请以站点最新公开规则为准。

## 页面功能

| 功能 | 说明 |
| --- | --- |
| 分组式排行榜表格 | 将在线率与延迟合并为运行质量，将退款与发票合并为服务政策 |
| 搜索 | 支持站点名、域名、模型厂商和支付方式 |
| 模型筛选 | 按 Anthropic、OpenAI、Google、DeepSeek 等厂商筛选 |
| 服务筛选 | 筛选支持退款、发票或两者都支持的站点 |
| 多维排序 | 按综合排名、在线率、延迟、模型数量和用户评分排序 |
| 移动端表格 | 保留语义化表格和固定核心列，可横向浏览完整数据 |
| SEO 静态预渲染 | 生成器把 `data.json` 的全部站点写入 HTML，搜索引擎无需执行 JavaScript |
| 渐进增强 | 静态表格始终可读，JavaScript 只增强搜索、筛选和排序 |

## 生成静态 HTML

`data.json` 是唯一的数据源。不要手动维护 `index.html` 中的排行榜行、榜单摘要或 JSON-LD；执行生成脚本即可一次更新全部 SEO 内容：

```bash
npm run build
```

生成器会同步更新：

| 输出内容 | 作用 |
| --- | --- |
| 86 条完整 `<tr>` | 站点名称和指标直接存在于 HTML 源码 |
| SEO 榜单摘要 | 自动写入前三名数据和前十五名名称 |
| JSON-LD `ItemList` | 为全部站点生成结构化排名数据 |
| 页面统计 | 更新站点数、平均在线率、平均延迟和厂商数 |
| Meta description | 自动写入最新前三名和站点总数 |
| `sitemap.xml` | 更新数据快照日期 |

如需先从上游仓库同步最新 `data.json` 再生成页面：

```bash
npm run sync
```

`.github/workflows/update-ranking.yml` 每 6 小时自动执行一次同步和预渲染；数据发生变化时，会由 GitHub Actions 自动提交 `data.json`、`index.html` 和 `sitemap.xml`。

## 发布到 `aiapirank.github.io`

当前远程仓库名是 `aiapirank/ai-ranking`。如果保持这个名字，GitHub Pages 地址会是：

```text
https://aiapirank.github.io/ai-ranking/
```

如果需要根地址：

```text
https://aiapirank.github.io/
```

GitHub 仓库必须命名为：

```text
aiapirank/aiapirank.github.io
```

操作步骤：

1. 在 GitHub 仓库的 **Settings → General** 中，把仓库名从 `ai-ranking` 改为 `aiapirank.github.io`。
2. 更新本地远程地址：

   ```bash
   git remote set-url origin git@github-airank:aiapirank/aiapirank.github.io.git
   ```

3. 推送 `main` 分支。
4. 打开 **Settings → Pages**。
5. 在 **Build and deployment** 中选择 **Deploy from a branch**。
6. 选择 `main` 和 `/(root)`，保存。
7. 等待 GitHub 完成首次部署，然后访问 `https://aiapirank.github.io/`。

GitHub Pages 默认使用 HTTPS。访问 `http://aiapirank.github.io/` 时会跳转到 HTTPS。
